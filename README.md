# Лендинг 3 — FAE-3920

Next.js App Router, TypeScript, Tailwind CSS. Вісім погоджених секцій, українська мова. Збірка й розробка використовують Webpack; Turbopack не вмикається.

## Локально

Потрібен Node.js 24.x. Виконайте `npm ci`, скопіюйте `.env.example` у `.env.local` та заповніть серверні змінні. Справжні ключі не додавайте до Git. `npm run dev` запускайте лише вручну.

```sh
npm run typecheck
npm test
npm run build
npm start
```

Окремий лінтер не налаштований. `npm test` перевіряє валідацію, формат запиту, помилки CRM, відсутність хибного успіху та SEO. Всі CRM-запити підмінено mock-функціями; реальні заявки тести не створюють.

## CRM: API з productId

Браузер надсилає ім’я, телефон і UUID запиту лише на власний `/api/order`.
Сервер перевіряє контакти й UUID та викликає `POST /api/leads` CRM з
`Content-Type: application/json` та серверним `x-api-key` із LANDING_API_KEY.
Ключ не передається браузеру й не додається до Git або NEXT_PUBLIC_*.

```json
{
  "customerName": "…",
  "customerPhone": "+380…",
  "productId": "cmwpgamza0001ukr2ru9od6km",
  "quantity": 1,
  "source": "Лендинг 3",
  "requestId": "<UUID v4>"
}
```

productId береться тільки з серверної змінної LANDING_PRODUCT_ID.
CRM отримує назву та ціну продажу з існуючого каталожного товару:
**Аварійна LED-лампа FAE-3920 із вбудованим акумулятором**, **299 грн**.
Кількість 1 задається сервером. Підставлені браузером productId, quantity,
price, productName та landingId ігноруються. landingId, назва та ціна до CRM
не передаються. Реєстр Landing і міграція його ціни для цього запиту не потрібні.
Поле source збережене для атрибуції «Лендинг 3».

Успіх показується лише після HTTP 2xx, `success: true` та непорожнього orderId CRM.
Помилки API, невідомий/неактивний товар, timeout або збій мережі зберігають поля
та не показують хибного успіху. Серверний timeout — 45 секунд.
Подвійне натискання блокується. Повтор зі сторінки з тими самими контактами
використовує той самий requestId; автоматичних повторів немає.
ID спроби діє до перезавантаження сторінки. Контакти не зберігаються у браузері.

## Змінні середовища Render

| Змінна | Значення |
| --- | --- |
| CRM_LEADS_ENDPOINT | https://autogid-uuug.onrender.com/api/leads |
| LANDING_API_KEY | Серверний секретний ключ CRM; не додавати в Git або NEXT_PUBLIC_* |
| LANDING_PRODUCT_ID | cmwpgamza0001ukr2ru9od6km |
| SITE_URL | https://led-lamp.onrender.com (до збірки) |
| NODE_ENV | production |
| PORT | Надається Render |

LANDING_ID більше не читається; застарілу змінну можна видалити з Render.
Без endpoint, ключа або LANDING_PRODUCT_ID сервер повертає 503 до виклику CRM.
Перед публікацією лендингу CRM має бути оновлена до версії, яка обробляє
productId незалежно від реєстру Landing (комміт e0a8c90 або новіший).
На Render LED-Lamp задати наведені змінні та перебудувати/розгорнути актуальний main.
Каталожний товар має бути активним із ціною продажу 299 грн.
Жодних товарів або заявок автоматично не створювали, production-базу не змінювали.

## SEO та швидкість

Задані погоджені title і description, `lang="uk"`, Open Graph `uk_UA`, Twitter Card. Product JSON-LD містить лише назву, характеристики та ціну 299 UAH, без рейтингу, відгуків або наявності. Збережені H1/H2/H3 й alt. Соціальні картинки використовують реальний `SITE_URL` після його налаштування.

Hero завантажується пріоритетно; нижні фото — ліниво через `next/image`, з `sizes`. Оригінали не змінені. WebP створюється механізмом Next.js. Клієнтські компоненти — лише галерея та форма, решта секцій рендериться на сервері. Нових runtime-бібліотек немає. In-memory кеш Next.js обмежений 16 MiB. Запускається один production-процес без фонових сервісів. Перевіряйте RAM у Render під реальним навантаженням; розмір кешу не є обмеженням усієї пам’яті процесу.

## GitHub — вручну

1. Створіть порожній репозиторій у своєму GitHub.
2. У папці проєкту виконайте `git init`, потім `git add .`.
3. Перевірте `git status`: не має бути `.env.local`, ключів, `node_modules` або `.next`. `.env.example` із порожнім ключем потрібно зберігати.
4. Виконайте `git commit -m "Prepare Landing 3 for production"` та `git branch -M main`.
5. Додайте адресу **свого** репозиторію через `git remote add origin <URL>` і виконайте `git push -u origin main`.

Автоматично репозиторій/сервіс не створювалися, push і публікація не виконувалися.

## Render Web Service — вручну

1. Оберіть **New → Web Service**, підключіть GitHub і потрібний репозиторій/гілку. Тип — **Node**, не Static Site.
2. Root Directory порожній, якщо проєкт у корені репозиторію.
3. **Build Command:** `npm ci --include=dev && npm run build`.
4. **Start Command:** `npm start`.
5. Додайте змінні з таблиці; `PORT` залиште під керуванням Render. Node 24.x заданий у `package.json`.
6. Після отримання справжньої Render URL задайте її як `SITE_URL` і запустіть нову збірку. Після підключення постійного домену змініть значення та перебудуйте.
7. Перевірте головну сторінку, `/robots.txt`, `/sitemap.xml`, соціальні картки. Після оновлення CRM та лендингу перевірте LANDING_PRODUCT_ID і одну заявку вручну лише з дозволу користувача.

Офіційні джерела: [Next.js на Render](https://render.com/docs/deploy-nextjs-app), [PORT і 0.0.0.0](https://render.com/docs/web-services#port-binding).

## Перша контрольна заявка — лише вручну

1. Перевірте правильний товар, ціну та API-ключ у CRM.
2. Попередьте менеджера про одну контрольну заявку. Використайте власний номер або погоджений контакт.
3. Відкрийте Network, заповніть форму й натисніть кнопку один раз: має бути один POST до **свого** `/api/order`, без ключа чи прямого запиту браузера до CRM.
4. Під час запиту кнопка заблокована й показує «Відправляємо замовлення...». Успіх і очищення форми — лише після підтвердження CRM.
5. Перевірте в CRM ім’я, телефон, FAE-3920, 299 грн, 1 шт., джерело «Лендинг 3» і правильний Product.id. За розбіжності призупиніть приймання заявок і перевірте LANDING_PRODUCT_ID та назву/ціну товару в каталозі CRM.
6. За помилки поля зберігаються й доступна повторна спроба. За тайм-ауту спершу перевірте CRM; повтор із незміненої сторінки використовує той самий requestId.

Автоматичні перевірки не створюють заявки у робочій CRM.

## Результати фінальної перевірки

- `npm run typecheck`, `npm test` (9 перевірок), `npm run build` — успішно. Окремого лінтера немає.
- Production-сервер стартує через `npm start`, зчитує `PORT=3103`; після перевірки зупинений. Dev-сервер не запускався.
- Браузерні вимірювання при viewport 320, 375, 390, 430, 768, 1024, 1440 px: горизонтального переповнення немає. Перевірені галерея, активна мініатюра, всі три якорі, плавна прокрутка, помилки обов’язкових полів та доступність кнопки форми над мобільною панеллю після завершення прокрутки. CSS і композиція не змінювалися.
- HTTP-перевірки: головна сторінка, robots і sitemap повертають 200; GET `/api/order` — 405; POST із порожніми контактами — 400 без звернення до CRM.
- Hero для ширини 640 px віддається у WebP: 20 248 байтів замість оригінальних 154 846 байтів. Оригінал збережено. Це локальна перевірка оптимізації, не оцінка Lighthouse або гарантія швидкості мобільної мережі.
- Серверний ключ у файли проєкту не внесений. Інтеграція використовує LANDING_PRODUCT_ID і каталожну ціну 299; перевірки виконуються з mock-CRM без робочих заявок.


## Анонімна аналітика лендингу (локально підготовлена)

VisitTracker не рендерить елементів і не змінює дизайн. На відкритті сторінки
створюється UUID у first-party localStorage `autogid.anonymousVisitor`.
Повторні відкриття використовують той самий ID. Якщо storage заблокований,
аналітика пропускається; оформлення замовлень продовжує працювати.
Дані контактів та IP для аналітики не зберігаються. Очищення storage, інший
браузер або інший origin створюють нового анонімного відвідувача.

Браузер викликає лише POST `/api/visit` з visitorId. Сервер додає Product.id із
LANDING_PRODUCT_ID, URL із SITE_URL та x-api-key із LANDING_API_KEY і викликає
`/api/landing-visits` CRM. Endpoint виводиться з CRM_LEADS_ENDPOINT.
Жодних нових змінних або LANDING_ID не потрібно. За відсутності SITE_URL
використовується відомий URL https://led-lamp.onrender.com; для копії лендингу
на іншому домені обов’язково встановити її власний SITE_URL до збірки/запуску.
URL/productId з браузерного payload не приймаються. Query/UTM/fragment не
ділять статистику однієї сторінки та не зберігаються в URL аналітики.

Серверний `/api/order` зберігає робочу схему productId/quantity/requestId та додає
необов’язкове поле landingUrl з тієї самої серверної конфігурації. CRM використовує
його лише для атрибуції; назву, ціну, статус і номер заявки визначає попередній
обробник замовлення. Збій аналітики не перетворює успішне замовлення на помилку.

Розгортати після підтвердження користувачем: резервна копія Neon → перевірка
pending-міграцій CRM (landing_price та landing_analytics) → їх окремо погоджене
застосування → нова CRM → новий LED-Lamp. До міграції ці нові структури не
використовувати для висновків про відвідуваність. Попередні заявки без URL
не переписуються і не розподіляються між лендингами заднім числом.
Автоматичні перевірки використовують тільки mock-CRM; реальних подій і замовлень
не відправляють. Push/deploy у межах підготовки аналітики не виконуються.
